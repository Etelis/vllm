The frontend ceiling

vLLM's OpenAI API server is one asyncio loop, so it gets one core. Rendering stream deltas from a per-stream template instead of a Pydantic model raises that ceiling by a third.

Output throughput +34.9% 33,411 → 45,061 tok/s, frontend-bound
Frontend CPU −25.7% 30.21 → 22.44 µs per streamed token
Wire differences 0 11 arms, 150 frames, one digest
FINDING

Why a microsecond per token moves throughput

Each streamed token builds a CompletionStreamResponse, validates it, and serializes it — 7.5 µs of Python, of which 4.2 µs is model construction. Everything in that frame except the choice index and the delta text is constant for the whole stream.

That cost would be uninteresting if the API server could spread it across cores. It cannot: the server is a single asyncio event loop, so one process is confined to one core. Across every baseline arm measured here the frontend sat at 1.006–1.013 cores — saturated, whether or not it was pinned there.

So the frontend's throughput is simply the reciprocal of its per-token CPU cost, and the measurements say exactly that:

Predicted from CPU alone: 10⁶ ⁄ 30.21 µs = 33,102 tok/s. Measured: 33,411. After the change, 10⁶ ⁄ 22.44 = 44,563 predicted against 45,061 measured — both within 1.5%. The API server, not the client and not the GPU, is what binds.

CORRECTNESS

Byte-identical on the wire

Every arm captured raw SSE bytes off the socket for the same greedy request set. After normalising the two fields that are per-request by definition — id and created — all eleven arms across all three render paths hash to a single digest over 150 frames.

1b901c44fdf95379  ← a1_m0 a1_m1 a1_m2 a2_m0 a2_m1 a2_m2
                     b1_m0 b2_m2 b3_m0 b4_m2 smoke
DISTINCT STREAMS: 1

The derived variant earns this structurally rather than by assertion: it renders one probe chunk through the real models and splits the result on sentinels, so a field added to CompletionStreamResponse is absorbed automatically instead of silently diverging from a hand-transcribed field list.

SCOPE

What this does and does not claim

  • The ~8 µs/token saving is pure Python string work: it is independent of model and hardware. Whether it becomes throughput depends on the frontend being the constraint — on a large model at modest request rates, it returns CPU rather than tokens.
  • --api-server-count defaults to data_parallel_size, so a single-frontend deployment — the configuration measured here — is the default for any non-DP server.
  • Only /v1/completions is covered. Chat completions has the same per-chunk envelope waste and is the busier endpoint; it is the obvious follow-up, not part of this measurement.
  • The fast path handles plain delta chunks only. Echo, logprobs, token ids, continuous usage and every terminal chunk keep the model path unchanged.
METHOD

Protocol

One patched file was installed for every arm, its behaviour selected at import time by an environment variable, so arms differ only by environment and never by bytes on disk. Arms were alternated to spread any drift across all three paths. Frontend CPU was read directly from /proc/<pid>/stat across the measured window; --ignore-eos fixed the token count per request so every arm streamed exactly the same number of frames.

vllm serve Qwen/Qwen3-0.6B --api-server-count 1 --max-num-seqs 512
vllm bench serve --dataset-name random --random-input-len 32 \
  --random-output-len 512 --ignore-eos --num-prompts 4000 --max-concurrency 512
