vLLM · streaming completions · 8 models · 1×H200

The frontend ceiling

vLLM's OpenAI API server is one asyncio loop, so it gets one core. Rendering stream deltas from a per-stream template instead of a Pydantic model cuts what that core spends per token by ~30% — on every model from 360M to 120B.

Frontend CPU / token −28% ~30 → ~22 µs, on all 8 models
Throughput, when FE-bound +27–38% 4 of 8 models; unchanged on the rest
Frames per token 0.98 vs 0.74 stock — stock coalesces under load
RESULT

A per-frame cost, not a per-model one

Each streamed chunk builds a CompletionStreamResponse, validates it, and serializes it — 7.5 µs of Python, of which 4.2 µs is model construction. Everything in that frame except the choice index and the delta text is constant for the whole stream.

Because it is per frame, the saving does not care what model is behind it. Across eight models spanning 360M to 120B and four tokenizer families, stock frontend CPU per streamed token lands between 29.0 and 32.4 µs, and the template lands between 20.5 and 22.9 µs. That is the load-bearing result.

One number predicts the whole table. Every model whose stock frontend drew ≈1.00 cores gained 27–38% throughput; every model below that gained nothing. SmolLM2-1.7B at 0.916 cores is the boundary case, and it gets nothing. The API server saturates near 10⁶⁄30 ≈ 33k output tok/s per process; above that line the change buys tokens, below it the change buys back CPU.

CAVEAT

An existing flag already buys the throughput

--stream-interval is merged upstream and attacks the same cost with a bigger lever: it emits one frame per N tokens. Setting it to 2 lifts the stock server from 32,446 to 43,599 tok/s on its own — the same win, for free, today. At stream_interval ≥ 2 this change adds no throughput at all.

But look at what the flag spends to get there.

The flag buys throughput by coarsening the stream; the template does not. At stream_interval=2 clients receive deltas in pairs (0.499 frames/token), at 4 in quads. The template reaches the same throughput while delivering 0.983 frames per token. The two compose: on top of stream_interval=2 it still cuts frontend CPU 22.6%, and 16.9% at 4.

There is a second finding hiding in that column. At the default stream_interval=1 the stock server does not actually deliver one frame per token under load — it delivers 0.741. Its own serialization backlog delays delivery, so vLLM merges undelivered deltas. The stock server is silently coarsening streams that the operator asked to be per-token; the template is what makes stream_interval=1 mean what it says.

CONTROLS

What was checked, and what was wrong

  • The baseline is honest. The pristine unpatched file gives 33,968 tok/s / 29.70 µs; the patched file with the fast path disabled gives 33,859 / 29.78 — 0.3% apart. The added branch costs nothing, so the A/B measured the intended thing.
  • Every arm ran byte-identical code on disk, with an environment variable selecting the path at import, so arms never differed by bytes.
  • Correction — nothing was ever CPU-pinned. An earlier version of this report described a "frontend pinned to one core" arm. The container's cpuset is 10,12,…,104; taskset -c 0 failed with EINVAL in every arm and the failure was not checked. All arms ran unpinned. The conclusion survives and is stronger for it: the frontend drew ≈1.01 cores with 32 available, which is the direct evidence that one process cannot exceed one core.
  • The CPU window was audited and is clean. The idle draw of the frontend, measured over 5 s before each run, is 0.000 cores, so the wider CPU-collection window contributes nothing to the per-token figures.
CORRECTNESS

Byte-identical, with one honest asterisk

Raw SSE bytes were captured off the socket for a fixed greedy request set in every arm. Normalising only the two per-request fields (id, created), all arms of a model hash to one digest — including the pristine unpatched server, which produces the same digest as the fast path:

1b901c44fdf95379  ctrl_pristine.sse  ctrl_mode0.sse  ctrl_mode2.sse
                  + all 11 Qwen3-0.6B arms, 150 frames
DISTINCT STREAMS: 1

Seven of eight models reproduced a single digest across every arm. The eighth (SmolLM2-360M) produced two, and the difference was not serialization: both streams carried the same 48 tokens and the same totals, but one merged " capital" and " of" into a single frame. That is the coalescing above — a timing-dependent frame boundary, not a content difference. The precise claim is therefore: identical bytes for the frames the fast path emits, verified per model by sha256 over raw socket bytes.

The template is derived by dumping one probe chunk through the real response models and splitting on sentinels, so field order and formatting track the models automatically. What it cannot track is a newly populated per-chunk field, so the test freezes both models' field sets — adding a field fails CI loudly and forces the fast path to be revisited.

METHOD

Protocol

Arms alternated, medians of two where repeated. --ignore-eos fixed output length so every arm streamed the same token count. Frontend CPU read from /proc/<pid>/stat (utime+stime) across the measured window.
